# 0. 全体像 — 成果物の系譜と3つの原則

```
requirements.md（正本の頂点。REQ-ID・スコープ宣言・DEC）
 ├─ 事実台帳: items.md（項目の事実）/ existing-tables.md（既存世界の事実）
 ├─ 設計台帳: db-design.yaml → process-design.yaml → meta-sync.yaml /
 │            ui-binding.yaml → migration.yaml
 ├─ オラクル（導出）: scenario/*.sql（DB状態）/ acceptance.md（画面挙動）
 ├─ 運用（導出）: backlog.md / questions.md / rejected.md
 ├─ ビュー（導出）: docs/design/*
 └─ 実装 → ビルド成果物（サイトパッケージ等）→ 引き渡しセット
```

**原則1: 正は1箇所。** すべての資料は「正本」か「導出物」のどちらか。
導出物への直接修正は次の再生成で消える — 指摘・修正は必ず正本に載せ、
導出物は再生成する。

**原則2: 検証は機械、判断は人間。** モデルの仕事は全数検分・突合・提案まで。
決定（○×）は人間。モデル生成の行を「決定済み」の顔で後工程に渡さない —
決定の出所（人間か生成か）を常に区別する。

**原則3: 禁止でなく契約で縛る（反省会 2026-07-30 の主結論）。**
「推測するな・発明するな」の禁止文はモデルの善意頼みで、単体では
不十分だった（実測: 要件からズレた提案の再生産、○×できないカードの
再提案ループ）。効いたのはすべて契約の形をしたもの — 読了証拠・
全行検分の表・母数報告。よって全プロンプトを3点セットで書く:
- **契約**: 対象・典拠・スコープの明示（外部情報・ツールを使うときは
  何をどこまで使ってよいかの契約）
- **DoD（完了の定義）**: 機械的に判定できる完了条件。「完了」を
  自己申告させない — 母数は現物・台帳から
- **証拠付き実行結果**: 報告には「何を読み・何を実行し・どこまで
  完了したか」の証拠（引用・件数・カバレッジ・実行ログ）を必須にする。
  証拠のない報告・提案は無効として扱う
禁止文は補助（最後の柵）であり、主役は契約・DoD・証拠。

**○×カードの成立条件（DoD）**: 人間が○×だけで判断できる形になって
いないカードは無効 — 各案に ①根拠（典拠の引用） ②影響（作業量・
波及1行） ③要件整合（原文を変えずに成立することの提示）が揃うこと。
揃わないカードは「再提案」でなく「無効・作り直し」として突き返す。

# 1. 資料カタログ — 各資料の性格と更新規則

| 資料 | 性格 | 更新経路 | 検証器 |
|---|---|---|---|
| requirements.md | 正本の頂点 | 人間の決定のみ（DEC-xx 追記。REQ 本文の変更は要件変更手続き→全層スイープ） | C1 |
| items.md / existing-tables.md | 事実台帳 | 現物からの抽出＋実在確認。source と根拠の両方を書けない行は入れない | C2 / C5 |
| db-design.yaml | 設計台帳（凍結） | 差分提案→人間承認→反映→該当層のみ再検証。全要素に evidence 必須 | C3 / C4 / C5 |
| process-design.yaml | 設計台帳（凍結） | 同上。rule は要件原文の引用主義 | C6 / C7 |
| meta-sync.yaml 等の連携台帳 | 設計台帳 | 同上。正は1箇所・流れは1方向 | C8 |
| migration.yaml | 設計台帳 | 同上 | C9 |
| scenario / acceptance | 導出オラクル | **手で直さない**。台帳が動いたら波及分のみ再生成→実行確認。実装の都合で曲げるのは禁止 | C10 / C11 |
| backlog.md | 導出＋状態 | 再生成時は状態列を ID 突合で引き継ぐ。完了には証拠必須 | C12 |
| questions.md / rejected.md | 運用台帳 | 未確定は Q-xx で駐車（新しい状態語の発明禁止）。却下案は方向ごと記録し再提案禁止 | C1(参照整合) |
| docs/design | ビュー | 手で直さない。台帳から再生成、件数自己検査付き | C13 |
| 実装コード | 成果物 | 完了条件は「scenario 一致」。テストを通すために台帳側を書き換えるのは禁止 | scenario 実行 |
| ビルド成果物（パッケージ等） | 導出物 | 生成器は1箇所のみ（品質ゲート込み）。再生成＝生成器の再実行、旧版は削除 | 生成器内の自己検分 |

台帳群は git 管理必須。マイルストーン（検証○・差分承認）ごとにコミット —
誤削除を常に「checkout 1回」の事故にしておく。

# 2. 変更反映マトリクス — 「何が変わったら、どれとどれを直すか」

| 変更の種類 | 正本への反映 | 再生成する導出物 | 再検証 | 禁じ手 |
|---|---|---|---|---|
| 要件変更 | REQ 変更＋DEC 記録 | evidence 逆引きで波及台帳へ差分→scenario/acceptance/docs 再生成 | 全層スイープ1回（×層のみ個別に閉じる） | 逆引き外の「ついで修正」 |
| 業務規則・定義の決定 | DEC-xx 追記、rule から引用 | 該当 scenario 再生成・実行 | 該当層のみ | rule への直書き（引用なし） |
| DB 設計変更 | db-design へ差分（承認後） | DDL 再生成→DB 反映、scenario 波及分、docs | C3/C4/C7 該当分＋実行層 | DDL 直編集・制約外しでのエラー回避 |
| 処理設計変更 | process-design へ差分 | scenario 波及分、backlog 再生成（状態引き継ぎ） | C6/C7/C12 | backlog の手修正だけで済ます |
| 実装のみの修正 | 台帳反映不要と明記 | なし | 該当 scenario 再実行→完了証拠更新 | ついでに台帳を「合わせて」書き換える |
| 実装が上流の欠陥を発見 | 作業中断→差分提案の物質化→○× | 承認後に波及分 | 変更層のみ | その作業セッションの流れで直す |
| 画面・UI 資産の変更 | ui-binding 等へ後追い同期 | ビルド成果物の再生成 | スモーク＋収載検分 | 成果物（パッケージ）内の直接編集 |
| 設計変更の実装への反映 | — | scenario 更新→backlog 再生成→完了済みの再判定（scenario が変わった完了だけ実装経由で再実行） | 改修行きの件数が手戻りの正確な範囲 | 感覚での手戻り見積もり |

対話で「ゴリッと」直した修正は、セッション末に正規化する:
`指摘 / 修正内容 / 現在の反映先` を一覧→ルーティング
（決定→DEC / 項目の事実→items / 既存→existing / 構造→db-design /
処理→process / 連携→meta-sync / 移行→migration / 実装のみ→反映不要 /
体裁→生成テンプレ）→導出物は再生成。

# 3. トリアージ — 症状から処置へ

## 3.1 検証・報告の症状

| 症状 | 疑い | 処置 |
|---|---|---|
| ○報告だが根拠がない | 検証のサボり | ○は全行検分の表とセットのときだけ信用。表を要求 |
| 0件・対象なし報告 | 縮退（最安の逃げ道） | 全行と除外理由の対応付けを要求。0件は証拠とセットでのみ有効 |
| 母数0で○ | 空虚な○（空集合は全検証を通る） | 全検証に検分母数の報告を必須化。母数0は「対象消失の疑い」で×扱い |
| 「完了」だが範囲が狭い | 母数の自己申告 | 母数を現物・台帳から取り直してカバレッジのマトリクスで検算。母数の説明責任（対象外根拠 or 見落とし） |
| 処置したのに件数が動かない | 観測の故障 | 修正をやめて観測を点検: 突合先の同定 / 実体ファイルの全数検索 / 個票1件の現物引用 / 再計算の証拠。（a)編集が別ファイル (b)突合先が古い導出物 (c)前回リストの再掲 |
| 差分が全件同一カテゴリ | 系統誤差 | 1件ずつ裁かずパターンとして処置。属性の事実は典拠と機械照合 |
| 「対象外」「分類不能」の大量発行 | 分類語彙の権限・不足 | ラベルの発行権限を明示（機械判定か人間宣言か）。大量の分類不能は第5の語彙（例: 廃棄候補）の欠落 |
| 「無い」という報告 | 探索の片手落ち | 静的・動的（実行時生成）両方の探索証拠を要求。現に表示されている値には出所が必ずある |
| 集計が走行ごとに点滅 | 観測装置が汚染世界の内側 | どのチェックアウト・どの版で走っているかを先に固定（基線・scan-scope） |

## 3.2 実行時エラーの症状

| 症状 | 処置 |
|---|---|
| 何かが生成されない・処理されない | 段別観測: データの流れ（入力→処理→送信→結果）を段ごとに件数で観測し、最初に0になる段を名指し。修正はその後 |
| フィルタで全滅 | 条件が期待する値 vs 実データの distinct を並べて引用＋条件と台帳 rule の一致判定 |
| 値・ラベルの不一致 | 三者照合（画面 / 実装 / 台帳）— 正は台帳。互いに合わせない。同族を全選択肢で検分 |
| NOT NULL 違反 | 制約外し禁止。3分岐: 実装の渡し忘れ / 源泉が本当に空（required の実測根拠を再検討 or 補完規則） / 復旧・生成時の制約過誤 |
| 環境依存エラー（TLS・接続先） | 実効設定の観測（ファイルの記載でなく実行時の値）→期待値と差分→環境値は集約先で切替。ローカル回避はコードに焼かず設定で。本番疎通は要実機確認へ |
| インポート・取込の形式エラー | 判別実験: 既知の正しい入力をまず通す（入れば形式互換で原因は生成物→差分比較 / 落ちれば形式非互換→正の見本を実機から取得）。形式の正解は常に実物から |
| DB オブジェクト不在 | 定義の所在を全検索→3分岐: 未適用（適用）/ どこにも無い（発明禁止・○×）/ 方言不整合（修正案） |

## 3.3 エージェント運用の症状

| 症状 | 処置 |
|---|---|
| 「実装がない」等で停止 | try-first: 停止禁止でまず実行させ、失敗の実物で分岐。思い込みの調査より実行が速い |
| 同じ場所で内容の違う停止が反復 | 複数知識源の合流点。ミニ台帳（stage 分解）で穴を設計時に全部出す |
| 提案が要件からズレ続ける | 読了証拠の強制（出典付き事実3点、無い提案は無効）＋要件保存則（原文を変えずに成立する案のみ）＋却下台帳（同方向の再提案禁止） |
| ○×カードが判断できない・再提案ループ | カードの DoD 不備。成立条件（根拠引用・影響・要件整合）を課し、揃わないカードは「無効・作り直し」として突き返す（原則3） |
| 初回生成が0件で止まる | 実在制約×新設禁止のデッドロック。承認ループを1周挟む |
| 1対象=1成果物の機械的増殖 | 単位の再考（同期処理の単位は項目でなく起動条件×方向×源泉、など）。統合提案→○× |
| 台帳・ファイルの消失 | 全数棚卸し→git 復元→逆再構成（導出物から。evidence 欠損は {lost} 注記）→完了判定は過去の数字でなく現行台帳との整合スイープ |
| モデルの出来が悪い | 生成・検分・提案は上位モデル、機械的作業は下位。規律の遵守はモデル能力に依存する |
| 人間が迷子（どれを実行？） | 写経元を1箇所に固定: ファイル冒頭に「いま打つ1本（全文）」を置き毎回上書き。実行は常に直近指定の1本のみ |

# 4. モードと運用リズム

| モード | 局面 | 規律 |
|---|---|---|
| 測定 | プロンプト効果の改善期 | 新セッション・全再生成・1変数変更 |
| 確定 | 設計の収束期 | 成果物凍結・最小差分・単調減少（増えたら違反シグナル） |
| 構築 | 製品を出す期 | 動くこと最優先・決定は人間が実機/現物で直接・目標単位1本渡し・仮決めは積んで後○×・台帳は実物から後追い逆生成 |

- モード間はゲートで区切る: スイープ全層○（母数付き）＋全未決に置き場
  （今直す / 次モードで決める / 回答待ち / 引き渡し済み / 廃棄候補）。
  未決ゼロは目標でない — 置き場があれば通過。
- **サイズでモードを選ぶ**: 台帳機構は要素数十以上の大物のみ。小物は人間が
  直接決め、モデルは記録と整合チェック。
- **スコープは常に最小**: 大プロンプトの繰り返しはトークン・精度・再実行の
  3軸で損。チェックは辺ごと、修正は差分、検証は該当層のみ。
  **小さな変更に全体の再捜査をかけない** — 全層スイープはモードのゲート
  時のみ（反省会実測: 都度の全体再捜査が無駄とコストの主因の1つ）。
- **台帳と scenario は「作る」でなく「抽出する」**（反省会実測: 効果は
  あったが作成コストが利益を食いかけた）。手書き・対話往復での作成を
  避け、現物（HTML・コード・実データ・パッケージ）からの機械抽出＋
  人間の仕分けで作る。scenario は網羅でなく代表（正常系1本＋明記された
  異常系のみ）。要素数が少ない領域では台帳自体を省略し、人間の直接
  決定＋事後記録で足りる。
- **トラブル時の第一手は人間の目視**（ファイルを開けば10秒の事実に
  診断プロンプトを重ねない）。第二手は観測（修正禁止・件数と実物）。

# 5. 別プロジェクトへの持ち込み手順

1. **対象プロダクトの設定語彙を調べる**（自前の抽象語彙で枠組みを発明
   しない — 設計書はプロダクトの設定単位で書かせる）。
2. **典拠の閉じた集合を組む**: requirements（ID 付与・スコープ宣言）→
   items（現物から抽出、entry タグ・出所仕分け）→ existing（実在確認
   のみ）。無い事実は推測せず未確定に積む、を全プロンプト共通の前提に。
3. **規模述語と許可・禁止節**を要件に合わせて埋める（プレースホルダを
   空欄で走らせない — モデルの事前分布で埋まる）。
4. 設計フェーズ集のプロンプトを順に（生成→検証2体→統合→実行検証）。
   検証は必ず文脈を持たない別セッション/サブエージェント＋ファイルのみ。
5. 収束したらゲート→構築モードへ。ビルド成果物の形式典拠は必ず実物から。
6. 引き渡し: ローカルで閉じない検証は「実行者を問わない手順書＋合否述語」
   に整形して境界の向こうへ（実行者原則）。

# 6. パッケージの TODO（持ち越し）

反省会（2026-07-30）で確定した未解決事項。次の適用・改訂で扱う:

1. **状態分裂**: チャット側エージェントが台帳を直接読めない構造は
   持ち出し制約下では解消不能 — 往復コストの根本原因として受容し、
   「いま打つ1本」1箇所固定・○×の現地完結・転記の最小化で緩和する。
2. **台帳外の実装物クラス**: DB オブジェクト（ストアドプロシージャ・
   関数）が台帳に載っていなかった（実測）。db-design の語彙拡張か
   実装物台帳の新設が必要。
3. **引き渡しセットの型**: 手動設定手順書・要実機確認リストの標準
   フォーマット化（実行者を問わない1枚: 実行順・合否述語・記入欄）。
4. **E2E の機械化**: acceptance.md の TEST をブラウザ自動化＋DB 突合で
   自動実行する段（設計時の検証資産を実装検証に直結させる最終形）。
5. **下位モデル耐性**: 規律の遵守が上位モデル前提。契約・DoD・証拠の
   形式化（原則3）でどこまで下位モデルに耐えるかは未検証。
6. **契約・DoD・証拠の標準テンプレ**: 原則3を全プロンプト集に遡って
   適用する改訂は未実施 — 新規プロンプトから適用し、使う際に順次改訂。
