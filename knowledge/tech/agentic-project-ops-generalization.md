# 相談内容

業務で要件定義→E2E の開発を回すための「プロンプト・契約などのテンプレートが
揃ったパッケージ」を作りたい。動機: 「推測禁止」等の禁止文プロンプトを打つだけでは
不十分と実感した（特定フェーズに限らずすべての活動で）。最近の記事の主張とも一致 —
重要なのは「エージェントが外部の情報・機能を利用するときの契約」「何を調査・実行し
どこまで完了したかを示す証拠付きの実行結果」「DoD」の3点。

確定した要件:
- **既存の agentic-project-ops を育てる**（新規別パッケージにしない。正は1箇所）
- **型を問わず汎用**（DB台帳型に限らず、UIアプリ・既存改修などどの案件でも最初に取り出せる）
- **契約/DoD/証拠の3点形式を背骨にし、全活動へ適用**（フェーズの隙間埋めが主目的ではない）
- **形態は貼り付け用 Markdown 集のまま**（閉域・手転記・エージェント種別を問わない）

# 検討・調査

## 現状パッケージのギャップ分析（2026-07-30 時点）

1. **入口が欠落**: 全プロンプトが「REQ-ID 付与済み要件定義書が存在する」前提。
   ヒアリングメモ・既存資料から要件定義書を作るフェーズのプロンプトがない。
2. **出口が薄い**: 受け入れテスト仕様の生成（02-build-mode の 3）とスモークまでは
   あるが、E2E の実行→証拠記録→受入判定のプロンプトがない。
3. **語彙結合**: C1〜C13・設計プロンプトの大半が DB 台帳案件の具体名
   （items.md / db-design.yaml 等）に結合しており、「汎用」と言いつつ持ち込み時に
   汎用部分の選り分けが人間の頭に残る。
4. **外部利用契約が薄い**: TEMPLATE.md の契約に「外部利用」行が1行あるのみ。
   ツール・API・外部情報の許可範囲・記録義務の型としては未整備。

## 3案の比較

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A: コア/プロファイル二層化（推奨） | core/（契約カタログ＋汎用フェーズプロンプト 00要件〜30E2E受入〜90復旧）と profiles/db-ledger/（現行 prompts をほぼ移設） | 「型を問わず取り出せる」が構造で実現。現行資産は無傷 | core は実案件未検証から始まる（実測からの抽象化なので確度は高い） |
| B: 現行構造のまま増築 | 00/05 を追加し TEMPLATE を拡張 | 変更最小 | DB 具体名だらけのままで、選り分けが頭に残る |
| C: 契約カタログのみ深化 | TEMPLATE 拡張だけ、他は次案件まで待つ | YAGNI 最徹底 | 「要件定義→E2E が揃う」という目的を満たさない |

契約カタログ（案A/B/C 共通の核）: 現 TEMPLATE.md の作業契約に加えて
**外部利用契約**（ツール・API・外部情報の許可範囲・記録義務）・
**検証契約**（文脈を持たない別セッション検証者への委任形式）・
**報告契約**（証拠付き実行結果の形式）を型として揃える。

# 結論

案A（コア/プロファイル二層化）で確定（ユーザー承認済み）。設計の正本は
`agentic-project-ops/docs/specs/2026-07-30-core-profile-split-design.md`。

**knowledge 資産の統合（ユーザー要望「user-chat のナレッジ資料を活かした設計に」）**:
Explore サブエージェント2体（契約・検証・復旧系 / フェーズ系）で knowledge/ を
掃引し、約26文書の知見を設計へ配線した。スペックに「ナレッジ源泉マップ」
（部品×源泉×採ったもの、33行）を収録 — 実装時はマップ記載の文書を一次資料と
して参照する（発明しない）。主な配線:

- 契約カタログ: 完了述語・境界・逃げ道の3要素（[gpt-5.6 実測](/tech/gpt-56-prompting-essence.md)）、
  DoD の P/J/W 型分類と J型片側検定（[同時進行フロー](/tech/concurrent-req-design-impl-flow.md)）、
  機械の証拠とモデルの申告の分離（[観測→制御](/tech/observation-control-mapping.md)）、
  外部利用契約は許可リストでなく断面のカタログ化（[閉域ループ](/tech/closed-network-agent-dev-loop.md)）
- 00-requirements: 仮説提示型質問・考慮不足5分類（[高速ドメイン把握](/work/rapid-domain-onboarding.md)）、
  引き継ぎテスト完成判定（[業務プロセス構造化](/tech/business-process-structuring-for-llm.md)）、
  マスク再導出による穴検出（[Excel構造化](/tech/excel-data-structuring-for-ai.md)）
- 30-e2e: 状態マトリクスと合格の凍結（[UI検証ループ](/tech/ai-ui-verification-loop.md)）、
  台帳×突合の4値状態（[トレーサビリティ検証](/tech/excel-to-web-traceability-verification.md)）、
  N回×率（[evals](/tech/evals-for-practitioners.md)）
- 90-recovery: 保全→無変更再実行→尋問→3分岐→1変数（[プロンプト習熟の階段](/tech/prompting-mastery-ladder.md)）、
  MTTR≒0（[バースト実行設計](/self/burst-execution-design.md)）

見送り（次版へ）: 来歴4タグ全面移行・NFR レーン・反例バケツ。
サブエージェント報告はスポットチェック3/3合格（逃げ道 8/8→0/5・P/J/W・
skipped+reason 必須、原典一致）。

## 実装完了（2026-07-30、コミット a5d71a3..a4f52c6 の21コミット）

v2 実装が完走した。最終構成: ルート README（汎用の入口・フェーズマップ・検証章・
未検証マーク）/ core 6ファイル（contracts + 00/10/20/30/90）/ profiles/db-ledger
5ファイル（旧資産4本の無傷移設 + README）。

- 実行方式: subagent-driven-development を改変し、実装 = codex exec（stdin 渡し・
  ログ直書き）、タスクレビュー = 文脈なし Claude サブエージェント、という
  生成者と判定者のモデル分離で9タスクを直列実行。全タスクがレビュー1〜2周で
  クリア（fix round は各1回以内、最終レビューの must-fix 2件も1周で解消）。
- レビューが構造欠陥を毎回実際に検出した（例: 穴検出の母数が REQ 側だけで素材の
  沈黙が合格に見える / 「正解漏洩0件」が自己申告でしか満たせない / 契約スコープが
  自フェーズの診断手順を禁止する自己矛盾 / MTTR≒0 と無条件レビュー要求の衝突）。
  「問題を探せ」形式＋現物での機械検証再実行を依頼文に固定したことが効いた。
- 計画と現物の衝突2件は裁定で解決し台帳に記録（mv-only 制約 vs 旧参照0検査 →
  参照2行の最小修正を許可 / 計画の90対応表が 90-recovery 完成前の古い記述 →
  現物優先）。
- 繰越: 次版 TODO 筆頭は「必須シナリオ」未定義（30:90,95）・独立性の階梯の
  表現統一・読了証拠表の出力先明示。core は実案件未検証（README にマーク済み、
  次案件の通し適用で外す）。
