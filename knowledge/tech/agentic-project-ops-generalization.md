# 相談内容

業務で要件定義→E2E の開発を回すための「プロンプト・契約などのテンプレートが
揃ったパッケージ」を作りたい。動機: 「推測禁止」等の禁止文プロンプトを打つだけでは
不十分と実感した（特定フェーズに限らずすべての活動で）。最近の記事の主張とも一致 —
重要なのは「エージェントが外部の情報・機能を利用するときの契約」「何を調査・実行し
どこまで完了したかを示す証拠付きの実行結果」「DoD」の3点。

確定した要件:
- **既存の agentic-project-ops を育てる**（新規別パッケージにしない。正は1箇所）
- **型を問わず汎用**（DB台帳型に限らず、UIアプリ・既存改修などどの案件でも最初に取り出せる）
- **契約/DoD/証拠の3点形式を背骨にし、全活動へ適用**（フェーズの隙間埋めが主目的ではない）
- **形態は貼り付け用 Markdown 集のまま**（閉域・手転記・エージェント種別を問わない）

# 検討・調査

## 現状パッケージのギャップ分析（2026-07-30 時点）

1. **入口が欠落**: 全プロンプトが「REQ-ID 付与済み要件定義書が存在する」前提。
   ヒアリングメモ・既存資料から要件定義書を作るフェーズのプロンプトがない。
2. **出口が薄い**: 受け入れテスト仕様の生成（02-build-mode の 3）とスモークまでは
   あるが、E2E の実行→証拠記録→受入判定のプロンプトがない。
3. **語彙結合**: C1〜C13・設計プロンプトの大半が DB 台帳案件の具体名
   （items.md / db-design.yaml 等）に結合しており、「汎用」と言いつつ持ち込み時に
   汎用部分の選り分けが人間の頭に残る。
4. **外部利用契約が薄い**: TEMPLATE.md の契約に「外部利用」行が1行あるのみ。
   ツール・API・外部情報の許可範囲・記録義務の型としては未整備。

## 3案の比較

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A: コア/プロファイル二層化（推奨） | core/（契約カタログ＋汎用フェーズプロンプト 00要件〜30E2E受入〜90復旧）と profiles/db-ledger/（現行 prompts をほぼ移設） | 「型を問わず取り出せる」が構造で実現。現行資産は無傷 | core は実案件未検証から始まる（実測からの抽象化なので確度は高い） |
| B: 現行構造のまま増築 | 00/05 を追加し TEMPLATE を拡張 | 変更最小 | DB 具体名だらけのままで、選り分けが頭に残る |
| C: 契約カタログのみ深化 | TEMPLATE 拡張だけ、他は次案件まで待つ | YAGNI 最徹底 | 「要件定義→E2E が揃う」という目的を満たさない |

契約カタログ（案A/B/C 共通の核）: 現 TEMPLATE.md の作業契約に加えて
**外部利用契約**（ツール・API・外部情報の許可範囲・記録義務）・
**検証契約**（文脈を持たない別セッション検証者への委任形式）・
**報告契約**（証拠付き実行結果の形式）を型として揃える。
