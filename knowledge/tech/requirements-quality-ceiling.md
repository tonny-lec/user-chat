# 単一原理

要件定義の「レベルの高さ」は装飾や網羅性ではなく、次の一点に圧縮できる:

> **文書が単独で判定器として機能する度合い** — 「これは要求どおりか」という争いを、
> 人間への追加質問なしに、文書の特定の行を指すだけで決着させられるか。

操作的定義: **実装者と検収者が互いに会話せず、この文書だけを読んで、同じテストを書けるか。**
書けるなら高レベル、書けないなら（どれだけ分厚くても）低レベル。

# 頂点の現物3点（判定器化を別方向に極めたもの）

1. **スペースシャトル PASS ソフトウェア**（人命×監査の極み）—
   約 42 万行のコードに対し仕様書は数万ページ。仕様側で全てを決着させ、コーディングはほぼ転記。
   最後の 11 リリースの欠陥は合計 17 件。全変更に「なぜ・誰が・どこへ波及」を記録 [1]。
2. **seL4 マイクロカーネル**(数学の極み) — 要求を Isabelle/HOL の形式仕様で書き、
   C 実装からバイナリまで機械証明で接続。曖昧さが原理的に存在しない。検証可能性の人類最高点 [2]。
3. **IETF RFC**（相互運用の極み）— 文書だけを読んだ独立チームの実装が相互接続する。
   MUST/SHOULD の規格語彙（RFC 2119）[3]。判定器としての実地試験が毎日世界中で走っている。

自然言語要件の頂点**技法**は **EARS**（Rolls-Royce 発, Mavin 2009）:
遍在 / While（状態）/ When（イベント）/ If-Then（望ましくない挙動）/ Where（機能選択）の
5 構文に全要求文を制限する [4]。

# 見本に使った技法チェックリスト（業務システム規模への翻訳）

会話内で振込限度額引き上げ機能の見本スライスを提示。使った技法:

- 用語は**操作的定義**（例: 暦日合計 = Asia/Tokyo 00:00 区切り、予約振込は実行日算入）
- 全要求文を EARS 構文に制限し、**各要求に〈文/根拠/検証〉の3点セット**を付ける
- 検証は境界値で書く（限度額ちょうど成立・+1円拒否）
- **スコープ外を明記**（やらないこと+その理由）
- **未確定事項台帳**: 未確定 / 仮置き / 確定者 / 期限 / 遅れると何に波及するか
- **双方向トレース**: REQ↔業務要求、REQ↔テスト。孤立 REQ・孤立テストは lint で落とす

# 自作 skill（fifth）との接続

[[requirements-skill-review]] の fifth 版は頂点の半分を既に実装している:
確認セット（推奨デフォルト+修正されたら何が変わるか）= 未確定事項台帳、
Case Shaping の推奨方針/棄却解釈 = 根拠欄（rationale capture）。
頂点との残差は **文単位の判定可能性**（EARS+境界値つき検証欄）と**双方向トレースの機械 lint**
（同レビューのハーネス節で強度 3〜6 化可能と既に指摘済み）の 2 つ。
