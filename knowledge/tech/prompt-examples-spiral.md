# 相談内容

「Why Harness Engineering Is So Hard」という記事（ハーネスエンジニアリングの7つの構造的困難を論じるエッセイ）を読んだ流れで、
「どこかのモデルのガイダンスでは例は不要とあったはずなのに、一周回って例がまた必要になっている気がする」という直観の検討。

# 検討・調査

## 「例は不要」の出どころとスコープ

- o1 系の公式ガイダンス（few-shot を避けよ、簡潔に直接的に）と GPT-5 系の簡潔主義。
  Microsoft の Medprompt→o1 研究では few-shot が o1 の性能をむしろ下げた。
- 自前実測（[gpt-5.6 エッセンス](/tech/gpt-56-prompting-essence.md) の「簡潔指示の削除が三本柱」）とも整合。
- ただし元の主張のスコープは「**タスクの指定**に例はもう要らない。推論タスクでは例が
  表面パターンの模倣を誘発し自前の推論を潰す」だった。これが「例は不要」に過剰一般化されて流通した。

## 例が担ってきた仕事の3期区分

1. **GPT-3 期**: 例＝タスク指定そのもの。指示が通じないため in-context 模倣が唯一の操縦チャネル。例が「何をするか」を運ぶ。
2. **instruction-tuned〜推論モデル期**: 指示で「何をするか」は伝わる。例は冗長、推論タスクでは有害。「例は不要」期。
3. **ハーネス期**: 例が戻るが、運ぶのは「何をするか」ではなく「**境界が正確にどこか**」。taste・形式・判定境界の固定。

## 機構: 規則は領域、例は点

- 規則は出力空間に**領域**を定義する（「簡潔に書け」は半空間）。例は**点**を打つ。
- 弱いモデルは点がないと領域すら見つけられなかった（第1期）。
- 強いモデルは規則から領域に入れる — 単発タスクならそれで十分（第2期）。
- ハーネスエンジニアリングの敵は**規則を満たす領域の内側に残る分散**。製品は毎回同じ場所に着地する必要がある。
  その残差は言葉で圧縮できない（できるなら規則に書けている）ため、点＝例で固定するしかない（第3期）。
- 既存 knowledge の2箇所が独立に第3期用法へ到達済み:
  [lean-agile マッピング](/tech/lean-agile-concepts-ai-mapping.md)「具体例はプロンプトにおける最高密度の仕様」、
  [ルーブリック作成](/tech/rubric-from-llm-logs.md)「レベル記述は形容詞でなく実例アンカーで固定する」。

## 失敗モードの反転（螺旋の証拠）

- 第1期のリスク: 例の**外**に汎化できない。
- 第3期のリスク: 例が規則を**上書き**する（記事の「example wins」— 「Do not X」と書きながら X する例を置くと X が出る）。
- つまり例はプロンプト内で**規則より特権の高い言語**になり、例のキュレーションが新しいバグ面になる。
  これは第1期には存在しなかった事故。
- 「例 vs 規則の優先順位」は失敗観測で検証可能な仮説（禁止規則＋違反例の組で違反出現率を測る）。未検証。

## 例と eval の合流

[業務構造化の7点セット](/tech/business-process-structuring-for-llm.md)の「良い例・悪い例のサンプル集は few-shot 例と
eval データセットの両方に直結」の通り、第3期の例は**仕様であると同時にテスト**。
例の回帰は、ハーネス期の品質保証が「分布に対する率」（[eval 入門](/tech/evals-for-practitioners.md)）になったことと同じ現象の裏表。

## 付録: ハーネス困難記事の読み筋（既存 corpus との突き合わせ）

記事の7痛点の大半は既存 knowledge が機構レベルで先行:

| 記事の痛点 | 既存 knowledge の対応（記事より先まで行っている点） |
|---|---|
| 決定的テストが書けない | [eval 入門](/tech/evals-for-practitioners.md) — rubric×分布を「凍結入力×成功述語×N回×率」まで操作化 |
| 失敗は静かで段階的 | [失敗判定の4層](/tech/agent-failure-detection-layers.md) — 「事後の分類でなく事前の述語設計」への反転は記事にない |
| 加算の本能は罠 | [プロンプト力の階段](/tech/prompting-mastery-ladder.md)の「消去」。削除が効く機構は「散文の制約は干渉するが[機械の強制点](/tech/skill-to-harness-enforcement.md)は干渉しない」 |
| 土台が書き換わる | [モデル移行観測フロー](/tech/model-migration-observation-flow.md) — 「ベースラインは新モデル到着前にしか取れない」 |

記事側が持っていて corpus に薄いもの:

- **例は規則より強く操縦する**（本文書の主題として取り込み済み）。
- **「pain is the moat」**: ハーネスの困難は基質由来で除去不能だからこそ参入障壁になる、という事業論的反転。
  困難の各項目を「解くべき問題」と同時に「防御可能性の源泉」として読む視点。

記事への異議1点: 「見えない仕事」を社会的な税として諦めているが、
[観測基盤の構想](/tech/harness-observability-platform.md)の「淘汰には利用観測が要る」の方が射程が長い。
可視化の不在は独立した痛点ではなく、加算の罠の**原因の一つ**（消した規則の価値は誰にも見えないから削除が駆動されない）。

# 結論

- 例は「一周回って必要になった」のではなく、**必要性の種類が入れ替わった**（円ではなく螺旋）。
  タスク指定としての例は死んだまま。分散固定としての例が生まれた。
- 使い分けの線引き: 単発の推論タスクでは「例は不要」を今も信じてよい。
  毎回同じ着地が要る製品出力（ハーネス）では、規則で領域を絞った後の残差を例で釘打つ。
- 例は規則より特権が高い前提で扱う: 例セットのキュレーションを規則の推敲より優先し、
  規則と矛盾する例を最優先で検査する。例セットはそのまま eval 資産（仕様＝テスト）として二重利用する。
