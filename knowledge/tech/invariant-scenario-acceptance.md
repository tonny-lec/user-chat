# 相談内容

実装の細かな修正をどんどん打っていきたいが、2つの不安がある:
(1) 資料（台帳）反映だけが漏れる、(2) 細かい修正のし過ぎで実装が
バグまみれにならないか。そこで acceptance.md を「ユーザーの実操作・
データの成立条件・システム全体の流れ」を取り入れたシナリオテスト的な
状態にしたい。ただし普通のシナリオテストと違い**「こうなってはいけない」
という制約**を持たせたい。ゴール（あるべき姿）を検証する方法を確立し、
過程は検証しない。

# 検討・調査

## 概念の同定

ユーザーの構想は **シナリオテスト（事例ベース）＋不変条件（invariant /
安全性性質）の二層**に正確に対応する。

- **シナリオテスト（SCEN）**: 「この前提データで、この操作列をしたら、
  この終状態になる」— 良いことが起きることの確認。
- **不変条件（INV）**: 「どの時点のどの状態を切り取っても、この禁止状態は
  存在しない」— 悪いことが決して起きないことの確認。シナリオに紐づかない
  全状態制約なので、**どのシナリオも想定しなかった経路の破壊も網にかかる**。
  これが「修正の積み重ねでバグまみれ」への直接の答え。

## 設計の要点

1. **判定は終状態と不変条件のみ — 過程を検証しない**。SCEN の判定は
   操作後の画面＋DB 終状態だけにし、中間状態・内部経路は見ない。
   テストが脆くなる最大原因は過程の検証。過程を判定から外すことで、
   実装の細かい修正でテストが壊れなくなる（＝修正の高速回転と両立）。
2. **INV は「0件であるべき SQL」に落とす**。孤児レコード 0 件・状態矛盾の
   組合せ 0 件・二重計上 0 件など、1 本 1 クエリ。数秒で全件回るので
   **毎修正後に実行**できる。
3. **2速運転**: 修正のたび INV（秒）、ゲートで SCEN 全件（分）。
4. **抽出主義**: INV は発明せず台帳から抽出する。出所は requirements の
   DEC-xx / process-design の rule（事前・事後条件）/ db-design の制約。
   出所タグ必須、候補は人間○×。
5. **資料反映もれは別機構**: 修正の契約（DoD）に「台帳反映 <済|不要(理由
   1行)>」を報告 1 行として足す＋取りこぼしはゲートの整合スイープ
   （[C1〜C13](/tech/ledger-consistency-checks.md)）が拾う。毎回の重い
   突合はしない。

## 文書形式

```
INV-xx: <禁止状態の名前>
禁止状態: <自然言語1行>
検査: <SQL — 0件であるべき>
出所: DEC-xx / PROC-xx の rule / DB制約
```

SCEN は既存 TEST-xx を「前提データ → ユーザー操作列 → 終状態判定
（画面＋DB scenario 突合）→ 事後に INV 全件」の形に再編する。

## 機械化との接続

[Codex × Playwright MCP の E2E 自動化](/tech/playwright-codex-e2e-automation.md)
と直結する: SCEN → Playwright spec、INV → テスト teardown または単独
コマンドの SQL チェック。INV スイートは回帰網として毎修正後の定型実行に
組み込める。

# 結論

全体構図: **修正の高速回転を INV（毎回・秒）が守り、区切りを SCEN
（ゲート・分）が守り、台帳反映は DoD 1 行＋ゲートスイープが守る**。
「ゴール＝あるべき姿」は SCEN の終状態＋ INV の禁止状態リストとして
明文化される。

導入は現在の不具合修正＋#4c 再実行が片付いてから。順序案:
1. INV 抽出の1本（台帳から禁止状態候補を出所タグ付きで抽出 → 人間○×）
2. acceptance.md 再編の1本(TEST-xx → SCEN 形式、判定を終状態のみに)
3. Playwright 恒久化の1本（SCEN → spec、INV → SQL チェック）

## 導入プロンプト案 — INV 抽出（キュー投入はユーザー指定後）

```markdown
禁止状態（不変条件）の候補を台帳から抽出せよ。発明は禁止 — すべての
候補に出所を付けること。

1. 抽出源: requirements の決定事項（DEC-xx）/ process-design の各 PROC の
   rule（事前条件・事後条件）/ db-design の制約（一意性・参照整合・
   状態遷移）。この3つを走査し、「データがこうなってはいけない」という
   形に言い換えられるものを列挙せよ。
2. 各候補を次の形式で書け:
   INV-xx: <名前> / 禁止状態: <1行> / 検査: <0件であるべき SQL> /
   出所: <DEC-xx | PROC-xx rule | DB制約名>
3. SQL は実際にこの環境で1回実行し、現時点の件数を添えよ
   （0件でない INV は「既に破れている」— 修正対象の発見として個票）。
4. 出所が曖昧で自信がない候補は、確定させず「候補（推測）」として
   分けて提示せよ（○×待ち）。

報告: INV 候補 <n>（出所内訳: DEC <n> / rule <n> / DB制約 <n>）/
現時点で破れている INV <n>（個票）/ 推測扱い <n>
```
