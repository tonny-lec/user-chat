# 目的

過去の LLM とのやりとりを確認して、出力評価用のルーブリックを作る。
「何をまとめるべきか」を3段のテンプレートに固定する。

前提となる原則は [eval 入門](/tech/evals-for-practitioners.md) から:

1. **観点は設計せず採集する** — ルーブリックの観点をゼロから発明しない。
   過去ログの失敗1件＝観点候補1件。成功例は「何が効いたか」の対照群。
2. **判定できない観点はルーブリックに入れない** — 各観点は判定器
   （コード判定/人間判定/LLM-as-judge）とセットで初めて機能する。
3. **レベル記述は実例アンカーで固定する** — 「適切である」「十分に」等の形容詞は
   採点者ごとにブレる。レベルごとに実際のやりとり（カード番号）を貼って係留する。

# パイプライン

```
過去ログ → [テンプレ1] 抽出カード（1件1枚）
        → [テンプレ2] 集約シート（頻度×判別力で観点候補を選抜）
        → [テンプレ3] ルーブリック本体（観点×レベル×アンカー）
```

# テンプレ1: 抽出カード（やりとり1件につき1枚）

まとめる単位は「やりとり1件＝カード1枚」。会話ログの転記ではなく判定付きの蒸留。

```markdown
## カード #<連番>
- 日付 / モデル: <いつ・どのモデルか>
- タスク種別: <実装 / 調査 / 文書生成 / 要約 / … 自分の用途で分類>
- 依頼の要約: <1〜2行。プロンプト原文は貼らない>
- 期待した成果（成功述語）: <何が満たされれば成功だったか。
  当時暗黙だったなら今ここで言語化する — これがルーブリックの種になる>
- 実際の結果: <1〜2行>
- 判定: 成功 / 部分 / 失敗
- 成否を分けた要因: <出力のどの性質が効いたか。
  例: 指示の解釈ズレ / 網羅性の穴 / 形式不遵守 / 根拠の欠落 / 冗長さ>
- 証拠の抜粋: <判定の根拠になる出力の該当箇所。短く1箇所>
- 観点候補: <このカードが示唆する評価観点。なければ空欄でよい>
```

記入のコツ:

- 一番価値があるのは「期待した成果」欄。当時は暗黙だった成功条件を
  事後に言語化する作業そのものがルーブリックの原料になる。
- 「部分」判定のカードが最も情報量が多い（成功と失敗の境界線を教えてくれる）。
- 10〜20枚で一度テンプレ2へ進む。全ログを処理しきってから、にしない
  （カード化は2時間で打ち切る — 儀式化防止）。

# テンプレ2: 集約シート（カードが10枚程度たまったら）

```markdown
## 観点候補の集計
| 観点候補 | 出現カード# | 頻度 | 判別力(成否を分けたか) | 判定器 |
|---------|-----------|------|----------------------|--------|
| 例: 形式遵守 | #3,#7,#12 | 3 | 高(失敗3件すべての主因) | コード判定 |
| 例: 根拠の明示 | #5,#9 | 2 | 中(成功例にも欠落あり) | 人間→LLM judge |
```

昇格ルール:

- **頻度×判別力**の高い順に採用し、観点数は 5±2 に絞る。
- 判別力 = その観点の高低が成功カードと失敗カードを実際に分けているか。
  「あったら良さそう」だが成否と相関しない観点は落とす。
- 判定器はコード判定（grep・形式チェック等で機械判定できる）を最優先。
  LLM-as-judge を使う観点は、人間判定済みカード5件との一致率を先に測る。

# テンプレ3: ルーブリック本体（観点1つにつき1ブロック)

```markdown
## 観点: <名前>
- 何を測るか（操作的定義）: <出力のどの性質を・どう観測するか。1文>
- 判定器: コード判定 / 人間判定 / LLM-as-judge
- 重み: <配点または高/中/低>
- レベル定義:
  | レベル | 記述 | 実例アンカー |
  |-------|------|------------|
  | 4 | <観測可能な条件で書く> | カード#12 |
  | 3 | | カード#5 |
  | 2 | | カード#9 |
  | 1 | | カード#3 |
- この観点で測らないこと: <隣接する別観点との境界を1行>
```

記入のコツ:

- レベル記述は「〜が適切」ではなく「引用箇所が0件 / 1件以上 / 全主張に付いている」
  のような数えられる条件で書く。数えられないなら実例アンカーだけでもよい
  （アンカー比較法: 「カード#5 より良いか悪いか」で採点する）。
- 「測らないこと」欄は観点間のダブルカウント防止。1つの欠陥が
  複数観点で減点されると重み設計が壊れる。

# 運用

- ルーブリックは凍結せず、新しい失敗を観測するたびカード→集約→改訂のループに乗せる
  （失敗観測駆動。[プロンプト力の階段](/tech/prompting-mastery-ladder.md)の失敗5クラスと同じ運用）。
- ルーブリックが安定したら、コード判定できる観点はそのまま eval の成功述語に転用できる
  （[eval 入門](/tech/evals-for-practitioners.md)の「凍結入力×成功述語×N回×率」へ接続）。

# Examples

- 「Codex の実装出力がときどき使えない」→ 過去 20 やりとりをカード化 →
  失敗 6 件の主因が「形式不遵守 3・網羅性の穴 2・解釈ズレ 1」→
  観点は形式遵守（コード判定）・網羅性（人間判定）・解釈整合（LLM judge、一致率確認後）の
  3 つに絞り、レベルは各カードをアンカーに 4 段で定義。
