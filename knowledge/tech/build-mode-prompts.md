# 構築モードとは

測定モード（新セッション再生成・1変数変更）/ 確定モード（凍結・最小差分）に
続く第3のモード。適用局面: 設計が概ね固まり、残作業が構築（サイト作成・
つなぎ込み・実装消化）で、**進捗が手転記の往復コストに律速されているとき**。
移行の動機は実測 — 設計用の重い機構を小さい構築作業に当て続けた結果、
製品が進まなくなった（[運用コスト考](/tech/db-design-validation-from-requirements.md)の3条件）。

規律（設計モードと逆になる点に注意）:

- **動くこと最優先**。台帳更新・検証を都度やらない — マイルストーンごとに
  実物から逆生成（**実物が正、台帳がビュー** — 設計フェーズと向きが逆転）。
- **決定はユーザーがその場で直接**（Pleasanter 画面で項目を作る等）。
  設計書は後から実物基準で生成。
- **業務PC エージェントへは目標単位で1本渡し**（ステップ分解のプロンプト
  工場をやめる）。仮決めは止まらず積む・要件矛盾だけ禁止。
- **チャット側は詰まりの壁打ちとマイルストーン記録のみ**。

# 1. 垂直スライス（目標単位の1本）

```markdown
ゴール: <主要画面1つ> が Pleasanter 上で端から端まで動く状態を作れ。
（拡張HTML・mjs の配置 → API 疎通 → 保存が独自テーブルに入る →
一覧に反映）
進め方:
- 動かすことを最優先。台帳の更新・検証はするな（後でまとめて記録する）。
- 判断が必要なこと（項目の扱い・配置・変換など）はその場で止まらず
  仮決めして進め、「仮決めリスト」に `内容 / 仮の値 / 理由1行` で積め。
  ただし要件定義書と矛盾する仮決めはするな。
- 詰まったら、内容と試したことを「詰まりリスト」に1行ずつ記録し、
  進められる別の部分を進めよ。
報告: 動いたこと（何を操作したら何が起きるか）/ 仮決めリスト / 詰まりリスト
```

# 2. マイルストーン記録（動いた後の後追い同期）

```markdown
動いている実物を正として、台帳を後追いで同期せよ。
1. 実物の抽出: Pleasanter のサイト設定（項目・選択肢・配置）と、
   つなぎ込み済みの mjs の読み書きを抽出し、meta-sync.yaml・site-spec・
   ui-binding.yaml を実物どおりに書き直せ（evidence: {actual: <出所>}）。
2. 仮決めリストのうち○が付いた分を DEC-xx として requirements.md に記録。
   ×の分は実物側の修正タスクとして列挙せよ。
3. backlog.md の該当アイテムを完了に更新（完了根拠 = スモーク結果）。
4. 整合の粗検査を1回: 実物由来の台帳と db-design・process-design の
   矛盾を件数とパターンで報告（修正は差分提案で）。
報告: 同期した台帳 / DEC 追加 <n> / 完了 <n> / 矛盾 <n>（パターン）
```
