# 構築モードとは

測定モード（新セッション再生成・1変数変更）/ 確定モード（凍結・最小差分）に
続く第3のモード。適用局面: 設計が概ね固まり、残作業が構築（サイト作成・
つなぎ込み・実装消化）で、**進捗が手転記の往復コストに律速されているとき**。
移行の動機は実測 — 設計用の重い機構を小さい構築作業に当て続けた結果、
製品が進まなくなった（[運用コスト考](/tech/db-design-validation-from-requirements.md)の3条件）。

規律（設計モードと逆になる点に注意）:

- **動くこと最優先**。台帳更新・検証を都度やらない — マイルストーンごとに
  実物から逆生成（**実物が正、台帳がビュー** — 設計フェーズと向きが逆転）。
- **決定はユーザーがその場で直接**（Pleasanter 画面で項目を作る等）。
  設計書は後から実物基準で生成。
- **業務PC エージェントへは目標単位で1本渡し**（ステップ分解のプロンプト
  工場をやめる）。仮決めは止まらず積む・要件矛盾だけ禁止。
- **チャット側は詰まりの壁打ちとマイルストーン記録のみ**。

# 0. 移行前の全体チェック（ゲート）

構築モードに入る前に1回だけ実行。目的は「矛盾は直す・未決は置き場を
決める」— 未決ゼロは目標でない（きれい＝全部の未決に置き場がある状態）。

```markdown
構築モード移行前の全体チェックを実行し、「矛盾」と「未決」を全数
可視化せよ。修正はするな — 報告のみ。台帳は 02_metadata/ 配下にある。

## A. 整合性スイープ（全層・母数付き）
1. DB 層: 順トレース（スコープ宣言の対象外を除く全 REQ が満たされるか）＋
   削除審問（全行検分。keep の根拠は REQ|structural|external）
2. 処理層: カバレッジ（全 REQ がいずれかの process で実現されるか）＋
   使用審問（db-design 全列が reads/writes に現れるか・幽霊参照）
3. 同期層: meta-sync.yaml の source・field の実在 / 単一の正 /
   sync の process 実在
4. 移行層: store: 独自 の全列が migration.yaml にあるか / source 実在 /
   required: true の on_blank が補完・除外で確定しているか
5. 実行層: DDL を SQLite で実行し、scenario/*.sql を全件実行
6. 運用層: backlog と process-design の全数突合（欠落 / 重複 / 幽霊）/
   questions.md の Q 参照整合
各層 `判定(○|×) / 検分した母数 / ×の件数とパターン` の表。
母数0の○を禁ずる — 「対象消失の疑い」として×扱いで報告せよ。

## B. 未決の全数棚卸し（1枚の未決台帳に）
以下を全部集め、1件1行で `ID / 内容1行 / 出所ファイル / 分類`:
- questions.md の回答待ち Q 全件
- 承認待ち・未反映の差分提案（直近の「上流設計の問題」の差分提案の行方を
  必ず含めよ — 出ていなければ「未提出」と報告）
- 台帳・scenario・spec 内の 未確定(Q-xx) 全件と、Q-ID の無い未確定
  （Q 無しは無効 — 新規 Q 候補として別掲）
- 要実機確認リスト
- meta-sync の現状（draft 行 / 同期 PROC 5本の統合保留）
- acceptance.md の期待動作未定義（あれば）
分類は4値のみ: 今直す（矛盾・機械で直せる）| 構築モードで決める
（実機を触れば決まる: メタ項目・配置等）| 現場回答待ち（Q-xx）|
引き渡し済み（移行手順書等）。迷う件は「分類不能」とし理由1行。

報告: スイープのスコアカード / 未決台帳の件数内訳（4分類＋分類不能）/
×層の内容と「今直す」の全一覧（この2つだけは1行ずつ）
```

処置: 「今直す」を差分提案→承認で解消し、該当層のみ再検証。
「構築モードで決める」は仮決めリストの初期在庫として build 側へ引き継ぐ。
全層○（または×が全て「今直す」以外で説明される）＋全未決に置き場、で
ゲート通過 — 以後は 実装→台帳（#1→#2）のループへ。

## #0c 実装⇄台帳の突合（整地の最終段）

ゲート通過後・構築開始前に1回。既存実装（API・ジョブ・mjs）と台帳を
揃えておき、構築モード中の実装→台帳反映（#2）を微調整だけにする。
裁定基準: 乖離の正はコードでも台帳でもなく **requirements / DEC** —
コードが動いていて台帳が古いだけなら台帳更新（実物が正）、コードが
要件・決定と矛盾ならコード修正を backlog へ。

```markdown
実装済みコードと台帳を突合し、「実装→台帳の反映が微調整で済む」状態に
せよ。台帳は 02_metadata/ 配下にある。
1. 実装の棚卸し: 実装済みの API・ジョブ・mjs 改修を列挙し、それぞれ
   対応する PROC-ID（process-design.yaml）を対応付けよ。
   - 対応する PROC が無い実装 → 「台帳外実装」として列挙せよ
   - impl: 独自|バッチ で実装が無い PROC → 「未実装」として backlog と
     突合せよ（backlog の状態と一致しているか）
2. backlog との突合: 状態「完了」の各アイテムに実装と完了証拠
   （scenario 一致の記録）があるか。証拠なし完了・実装あり未完了を列挙せよ。
3. 挙動の突合: 実装済み PROC それぞれについて、コードの reads/writes と
   process-design の reads/writes の差分をテーブル.列単位で列挙せよ。
   scenario が実行可能なものは実装経由で実行し、一致を確認せよ。
4. 乖離の処置提案（勝手に直すな。裁定基準は requirements と DEC —
   台帳でもコードでもない）:
   - コードが動いていて台帳が古いだけ → 台帳更新の差分提案
   - コードが要件・DEC と矛盾 → コード修正の backlog アイテム提案
   - 判定できない → 判定に何が必要か1行
   `対象 / 乖離内容 / 提案（台帳更新 | コード修正 | 要判断）` の表で
   ○×カードにして提示し、この場で人間の○×を待て。
5. ○×後: 台帳更新分を反映し、使用審問と backlog 監査を再実行して
   差分のみ報告せよ。
報告: 実装 <n>（うち台帳外 <n>）/ 未実装 <n> / 証拠なし完了 <n> /
挙動乖離 <n>（パターン）/ 処置の内訳（台帳更新/コード修正/要判断）/
再検証 <○|×>
```

**実測（2026-07-28）**: 実装16 / 未実装2 / 証拠なし完了16（=全実装。
scenario は通るが記録が無いだけの可能性大 — 再実装でなく証拠の後追い記録で
解消する）/ 挙動乖離5 / 処置: 台帳更新5・コード修正1・要判断4。

**#0c-後処理（○×反映後に1本）:**

```markdown
実装⇄台帳突合の後処理。○×済みの処置を反映した上で、以下を行え。
1. 証拠なし完了16件: 各 PROC の scenario を実装経由で実行し、
   一致したものは backlog の該当行に完了証拠（scenario 名・実行日・一致）を
   記録せよ。一致しないものは既出の乖離カードと突合し、カードに無い
   新規乖離のみ ○×カードとして追加提示せよ。
2. コード修正1件: backlog に改修アイテムとして追加せよ（着手はするな）。
3. 未実装2件: backlog の状態が「未着手」であることと依存順を確認せよ。
4. 仕上げ: C12（backlog と process-design の突合・完了証拠）と
   C7（使用審問）を再実行し、差分のみ報告せよ。
報告: 証拠記録 <n>/16 / 新規乖離 <n> / backlog: 改修 <n>・未着手 <n> /
C12 <○|×> / C7 <○|×>
```

後続: 残実装（未実装2＋改修1）を 5.3 実装ヘッダで1件ずつ →
API・job 完了 → サイト作成（実機直接）→ 実機からパッケージエクスポート。

# 1. 垂直スライス（目標単位の1本）

```markdown
ゴール: <主要画面1つ> が Pleasanter 上で端から端まで動く状態を作れ。
（拡張HTML・mjs の配置 → API 疎通 → 保存が独自テーブルに入る →
一覧に反映）
進め方:
- 動かすことを最優先。台帳の更新・検証はするな（後でまとめて記録する）。
- 判断が必要なこと（項目の扱い・配置・変換など）はその場で止まらず
  仮決めして進め、「仮決めリスト」に `内容 / 仮の値 / 理由1行` で積め。
  ただし要件定義書と矛盾する仮決めはするな。
- 詰まったら、内容と試したことを「詰まりリスト」に1行ずつ記録し、
  進められる別の部分を進めよ。
報告: 動いたこと（何を操作したら何が起きるか）/ 仮決めリスト / 詰まりリスト
```

つなぎ込みで「ローカルのまま」で済まない典型4点（仮決め・詰まりの定番）:
①配置の分割 — 1つの HTML を拡張HTML枠・スクリプト・スタイルの各枠へ
分割、参照パス変更 ②モックの差し替え — ダミーデータ部を実 API 呼び出しに
結線（つなぎ込みの本体） ③コンテキスト取得 — 開いているレコード
（ItemId 等）を Pleasanter 画面から取る処理の新設 ④認証・オリジン —
拡張HTML→独自 API の認証方式と同一オリジン/CORS の確認。

# 1a. ローカル DB への DDL 反映（つなぎ込みの前提）

#1b のローカル確認はローカル DB にスキーマが無いと成立しない（実測
2026-07-28: 未反映のまま進んでいた）。注意2点: 検証用 DDL は SQLite 方言
なのでローカル DB の実エンジン用に yaml から生成し直す / 既存テーブルには
一切触れない（参照のみ）。

```markdown
db-design.yaml からローカル DB 用の DDL を生成し、反映せよ。
台帳は 02_metadata/ 配下にある。
対象 RDBMS と接続先: <ローカルDBの種類と接続先を記入>

- 生成対象は store: 独自 の新規テーブルとビューのみ。既存テーブル
  （existing-tables.md 記載）への CREATE / ALTER / DROP を一切含めるな —
  既存は参照のみ。
- DDL は db-design.yaml からの導出物として ddl/ に保存せよ。手編集を
  禁ずる — 直すときは yaml を直して再生成する。
- 反映前の安全確認: 接続先に同名テーブルが既に存在しないか確認し、
  存在する場合は反映せず停止して報告せよ（上書き禁止）。
- 反映後の検証:
  1. テーブル数・列数・ビュー数を db-design.yaml と突合せよ（件数一致）
  2. 型・NOT NULL・FK が設計どおりかを全行検分の表で示せ
  3. 代表1件: 実装済み API 経由で保存を1回行い、行が入ることを確認せよ
     （つなぎ込みのローカル確認の前提が整った証拠）
報告: DDL <テーブル n / ビュー n> / 反映 <成功 | 停止（理由）> /
件数突合 <一致 | 差分> / 全行検分 <○|×> / API 保存スモーク <通過 | 失敗>
```

**#1a 実測（2026-07-28）: DDL 生成失敗** — 抽象型（unspecified/integer/
string）の PostgreSQL 変換規則なし・PK/FK/unique/check 未定義・新規ビューの
SELECT なし。正体は db-design 復旧の残り傷（ビューは名前だけ復元・制約は
骨格復元で欠落）。復旧後スイープの実行層○は過去保存の SQLite 用 DDL で
走っていた疑い — **そのファイルが制約・ビュー定義の最良の復元典拠**。

**#1a-補修の実測（2026-07-28）**: 制約復元 a=24（過去 DDL から）/
b=27（structural 導出）/ c=0。補修後の #1a 再実行は 反映成功・件数一致・
全行検分○・API 保存スモーク通過 — b 導出の27制約も反映検証で実証済み。
ローカル DB 整備完了、#1b（つなぎ込み）へ。

**#1a-補修（DDL 生成の欠落解消）:**

```markdown
DDL 生成を阻む3つの欠落を解消せよ。db-design.yaml は凍結 —
変更は最小差分のみ。台帳は 02_metadata/ 配下にある。

1. 型変換規則: db-design.yaml に現れる抽象型（string・integer 等）を全て
   列挙し、`抽象型 / PostgreSQL 型 / 根拠1行` の変換表を提案せよ。
   承認後は type-mapping.md として保存し、以後の DDL 生成の典拠とする。
   型が unspecified の列は items.md の該当 ITEM の型を引いて解消せよ。
   items.md にも無い列のみ `列 / 提案型 / 実データ根拠 / 確度` で提案し
   人間の○×を待て（実測根拠なしの断定を禁ずる）。

2. PK / FK / unique / check: 以下の優先順で復元せよ:
   a. 過去のフェーズD・スイープ実行層で SQLite に流した DDL ファイル・
      スクリプトが残っていないか探せ。あればそこから制約を抽出せよ
      （最良の典拠）。
   b. 無ければ db-design.yaml の evidence: {structural: 主キー・FK・親表}
      と親子関係の記述から導出せよ。
   c. a・b どちらからも決まらない制約のみ、提案として人間の○×へ。
   復元した制約は db-design.yaml に最小差分で記入し、各行に復元元
   （a|b|c）を注記せよ。

3. 新規ビューの SELECT: 各ビューについて:
   a. docs/design（10-database 等）と過去の DDL ファイルに定義が
      残っていないか探せ。
   b. 無ければ、そのビューを参照する scenario/*.sql が要求する列・結合
      から SELECT を導出し、SQLite で該当 scenario が通ることを確認せよ。
   c. 導出できないビューは「定義不能: 何が決まれば書けるか1行」で報告せよ。

4. 解消後、PostgreSQL 用 DDL の生成を再試行せよ。生成できたら反映は
   まだするな — 生成成功の報告まで。

報告: 型変換表 <n 型>（○×待ち）/ unspecified 解消 <n>（残 <n>）/
制約復元 <n>（復元元 a/b/c の内訳）/ ビュー定義 <n>/<総数>（定義不能 <n>）/
```
